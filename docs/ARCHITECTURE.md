# Архитектура

## Границы модулей

| Папка                    | Ответственность                                                               |
| ------------------------ | ----------------------------------------------------------------------------- |
| `src/app`                | маршруты, загрузка каталога и общие состояния, необязательный WebMCP          |
| `src/features/auth`      | жизненный цикл Supabase session и роль                                        |
| `src/features/cart`      | чистые расчёты, идентичность товар+вариант, проверка сохранённой корзины      |
| `src/features/admin`     | редакторы товаров/фото/настроек                                               |
| `src/services`           | обращения к Supabase, независимые от маршрутов                                |
| `src/components`         | повторно используемые элементы интерфейса                                     |
| `src/pages`              | композиция конкретных экранов, lazy chunks                                    |
| `src/i18n`               | типизированный словарь и locale provider                                      |
| `src/config`, `src/data` | стартовые бизнес-настройки, редакционные тексты и явно отдельный demo adapter |
| `src/lib`                | Supabase client, validation, безопасное чтение browser storage                |
| `src/types`              | контракт доменных сущностей                                                   |
| `supabase`               | воспроизводимая серверная схема, grants, RLS, RPC и contact function          |

Новый экран добавляется в `app/App.tsx`, новый запрос — в сервис соответствующей области. Не следует добавлять обработку всех бизнес-процессов в StoreProvider. Отдельные feature providers вводятся по мере роста состояния; пока внешняя state-библиотека не нужна.

## Товары и расширение

UUID стабильны; slug — адрес карточки. Локализуемые поля содержат `tj` и `ru`. Характеристики `specs` расширяются без миграции, ключи пока редакционные (вводятся администратором). Структурированные фильтры представлены `capacity`, `type`, `features`, `category_id`. Для локализации каждой произвольной характеристики в будущем можно перевести values на `{tj,ru}` через версионированную миграцию.

Варианты имеют собственные цену и остаток. Удалённые из редактора варианты архивируются через `active=false`, чтобы сохранить ссылки заказов. Заказ хранит снимки названия, варианта и цены, поэтому редактирование или удаление товара не меняет историю.

Настройки магазина из `site_settings/store` перекрывают `config/site.ts`. Общие UI-строки лежат в `i18n/messages.ts`. Редакционные страницы — `data/content.ts`. После смены данных через админку общий каталог обновляется.

## Создание заказа

Frontend валидирует форму, обновляет товары корзины, передаёт UUID запроса и ожидаемый итог. RPC заново читает цены, проверяет опубликованность, блокирует товары в стабильном порядке, уменьшает остатки, создаёт заказ и позиции одной транзакцией. При несовпадении итоговой цены вся транзакция откатывается. Повтор одного UUID в аккаунте возвращает уже созданный заказ. Корзина очищается только после успешного ответа.

Текущий идентификатор повтора живёт на открытом экране checkout; после полной перезагрузки экрана формируется новый. При неоднозначном сетевом результате следует сначала проверить историю заказов. Будущий клиент может хранить устойчивый idempotency draft с отпечатком содержимого.

## Замена платформы

Pages зависит только от `dist`, router и Vite base. Supabase-запросы вынесены в `services`; компоненты и доменные типы можно перенести в SSG/SSR framework. Для большого каталога заменить `loadCatalog` на paginated query, сохранив ProductCard и DTO. Для платежей добавить серверную payment intent/webhook, не принимать статус paid от клиента.
